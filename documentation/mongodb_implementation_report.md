# MongoDB Persistence - Implementation Report

## 1. Why MongoDB was required

The dashboard could generate a vehicle analysis but nothing about it survived a
page refresh or a second analysis - there was no way to see a vehicle's
condition over time, which is the entire point of "predictive maintenance."

## 2. Previous limitation

Documented repeatedly across the project (`phase3_backend.md`,
`final_project_report.md`, `final_system_architecture.md`,
`final_project_validation.md`) as: MongoDB connection code not written, no
local MongoDB instance or running Docker daemon available to test against.

## 3. MongoDB architecture

```
React (:5173)
  -> Express (:5000)
       -> FastAPI (:8000/:8001) for ML   (unchanged)
       -> LLM provider dispatcher        (unchanged)
       -> backend/src/db/ (NEW)
            connection.js                  - connect once at startup, track status, reconnect-aware
            models/VehicleAnalysis.js      - Mongoose schema
            repositories/vehicleAnalysisRepository.js - validate + save/query
       -> MongoDB (new, real instance - see section 15)
```

`POST /api/report` and `POST /api/analyze` were **extended** (not duplicated)
to save after generating a result; 3 new routes added for retrieval.

## 4. Database technology/library selected

**Mongoose** (not the raw MongoDB Node driver). Reasoning: the project's
existing Express code (`routes/`, `llm/`) is already organized as small,
single-purpose modules; Mongoose's schema + built-in validation fit that style
directly and satisfy the task's own "validate incoming data before inserting"
requirement with less custom code than hand-rolling validation against the raw
driver.

## 5. Database schema / 6. Collection

Single collection: **`vehicle_analyses`**.

```js
{
  _id: ObjectId,
  vehicleId: String,       // promoted from vehicleContext.vehicle_meta.vehicle_id, indexed
  timestamp: Date,         // backend-authoritative, set at save time
  vehicleContext: Mixed,   // the EXISTING combined-output object, unmodified (anomaly/fault/driver_behaviour/vehicle_meta/schema_version)
  llmReport: Mixed,        // the EXISTING generateMaintenanceReport() return value, unmodified
  metadata: { savedAt: Date, source: String }
}
```

**Why `vehicleContext`/`llmReport` are stored as-is (Mixed) rather than
flattened into named fields:** their exact shape is owned by
`combined_inference.py` and the LLM providers, not by this schema. Flattening
would mean this file silently drifting out of sync every time either of those
changes (as already happened once this session with the fault-classifier
replacement) - storing the object whole keeps the database a true mirror of
what the rest of the system actually produces.

**Vehicle ID decision:** `vehicle_meta.vehicle_id` already existed in the
combined-output schema and was already stable ("demo-vehicle-01" every time the
sample is analyzed) - used directly, no new ID scheme introduced.

**Timestamp decision:** generated by the backend (`new Date()`) at save time,
never trusted from the request body.

**Indexes:** compound `{ vehicleId: 1, timestamp: -1 }` - matches the only two
query patterns that exist (history-by-vehicle sorted newest-first, latest-by-
vehicle). No other indexes were added without a concrete query to justify them.

**Save-on-LLM-failure decision:** yes, always save whatever
`generateMaintenanceReport()` actually returned (`live`, `mock`, or
`error_fallback`), honestly labeled. An incomplete record (no ML result at all)
can never reach the save step - `routes/analyze.js` already returns a 502
before that point if FastAPI itself fails. Full reasoning:
`mongodb_implementation_plan.md`.

## 9. Connection configuration

`backend/src/db/connection.js`: connects once at startup via `connectDB()`
(awaited before `app.listen()`), never throws (catches connection failure and
logs a clear message instead), exposes `isConnected()`/`getStatus()` for the
health endpoint and the repository layer, and listens for
`disconnected`/`reconnected`/`connected`/`error` events to keep that status
accurate as the underlying driver's connection state changes over time - not
just at the initial connect.

**A real bug was found and fixed here during testing:** the first version only
listened for `disconnected`/`error`, so after MongoDB came back up following an
outage, the reported status stayed stuck on `"disconnected"` forever even
though the driver had silently reconnected underneath. Found by actually
stopping and restarting the MongoDB container mid-session (see section 12),
fixed by also listening for `connected`/`reconnected`, and re-verified with the
same stop/start cycle.

## 10. Data flow

```
POST /api/report or /api/analyze
  -> (ML + LLM steps, unchanged)
  -> saveAnalysis(vehicleContext, llmReport)
       -> validate vehicleId format, object shapes, payload size
       -> if not connected: throw DB_UNAVAILABLE (caught by the route, never crashes the request)
       -> VehicleAnalysis.create({...})
  -> response includes both the normal result AND a `persistence` field
```

## 11. Error handling

- MongoDB down at startup -> backend starts anyway, logs it, `/api/health`
  reports `database.state: "disconnected"` or `"error"` with a message.
- MongoDB down during a save -> the ML/LLM result is still returned to the
  caller; `persistence: {saved: false, reason: "..."}` is attached instead of
  silently dropping the failure. **Actually tested** (section 12).
- MongoDB down during a history/latest/by-id read -> `503 {"error": "Database
  unavailable", ...}`, not a crash or a hang. **Actually tested.**
- Invalid `vehicleId` (bad characters) -> `400`. **Actually tested.**
- Invalid analysis `id` format -> `400`. **Actually tested.**
- Valid-format but nonexistent `id`/`vehicleId` -> `404` / empty history array
  (not an error - an empty result is a valid, not-wrong answer). **Actually
  tested.**
- Oversized payload (>256KB) -> rejected with `PAYLOAD_TOO_LARGE` before
  touching MongoDB (not independently triggered in testing - this project's
  real payloads are a few KB - but the code path exists and was read-reviewed).

## 12. Frontend changes

Additive only. `App.jsx` keeps its existing "Load Sample Vehicle Analysis"
button and all 4 existing result sections. One new section, **"Vehicle
Analysis History"**, added below Maintenance Report: a table (Date / Anomaly /

## 14. Limitations

- This MongoDB instance is a local, unauthenticated Docker container suitable
  for development/demo only - not configured with auth, TLS, or a production
  deployment topology. Fine for an 8-credit student project; would need
  hardening for anything real.
- Only 2-3 real analyses exist in the database right now (from this session's
  testing) - the history UI has not been exercised with a large volume of
  records.
- `vehicleId` is currently always `"demo-vehicle-01"` (the one value the
  dataset produces) - multi-vehicle behavior is implemented and would work
  correctly (the schema and queries are already vehicle-scoped), but has not
  been demonstrated with a second distinct vehicle ID since no second vehicle's
  data exists in this project.

## 15. How to run MongoDB

**Option A - Docker (what was actually used in this session):**
```bash
docker run -d --name predictive-maintenance-mongo -p 27017:27017 mongo:7
```
(omit `-d` to run in the foreground; add `-v mongo_data:/data/db` for a named
volume if you want data to survive `docker rm`, not just `docker stop`/`start`
- this session's container used Docker's default anonymous volume, which does
survive stop/start, as demonstrated in section 13 test 10, but not `docker rm`).

**Option B - MongoDB Atlas (free tier):** create a free cluster at
mongodb.com/cloud/atlas, get its connection string, and set
`MONGODB_URI=<your atlas connection string>` in `backend/.env`. No code changes
needed - `connectDB()` just connects to whatever URI is configured.

Only one option is required, not both.

## 16. How to run the complete application

```bash
# Terminal 1 - ML service
cd ml_service
uvicorn main:app --reload --port 8000   # see IMPORTANT note below

# Terminal 2 - backend
cd backend
npm install
npm start

# Terminal 3 - frontend
cd frontend
npm run dev -- --port 5173
```

**IMPORTANT, unrelated side-effect discovered in this session:** starting
Docker Desktop (needed for MongoDB) auto-started a pre-existing, unrelated
container stack on this machine (`compreface-ui`) that also binds host port
8000, which conflicts with FastAPI's documented default port. This was not
caused by MongoDB itself, but by Docker Desktop coming online. It was **not**
fixed by stopping that container (explicitly blocked by this environment's
safety controls, since it is not part of this project and stopping someone
else's running workload without clear permission is exactly the kind of action
that should not happen automatically). Instead, FastAPI was run on **port
8001** for the remainder of this session, with `ML_SERVICE_URL=http://localhost:8001`
set in `.env` to match. **If you run this on your own machine without that
pre-existing container, port 8000 is fine and no change is needed** - this is
an artifact of this specific development environment, not a change to the
project's design. If you hit the same conflict, either run FastAPI on 8001 (as
done here) or free port 8000 yourself.

## 17. How to verify history

1. Open `http://localhost:5173`.
2. Click "Load Sample Vehicle Analysis" - the existing 4 result sections appear
   as before.
3. Scroll down - a new "Vehicle Analysis History" table appears with at least
   one row (the analysis you just generated).
4. Refresh the page, click the button again - a second row appears, newest on
   top.
5. Click a row to expand its saved detail inline.
6. Check `GET http://localhost:5000/api/vehicle/demo-vehicle-01/history`
   directly in a browser tab or via curl to see the raw saved JSON.

(Steps 1-4 exercise exactly the real request chain verified via curl in
section 13 of this report - the frontend code was build-verified but not
visually re-tested in an actual browser in this session, consistent with every
earlier phase of this project; see `phase3_frontend.md` for that standing
caveat.)
